# Состояние проекта

Дата: 2026-10-18 (Asia/Yekaterinburg).

## Этапы 1 и 2

**Реализованы и проверены локально, включая Linux-контейнеры и настоящий браузер.**
Этап 3 не начат. Это основа системы с авторизацией и интерфейсом; складские операции,
реестр оборудования, перемещения, обслуживание, XLSX и импорт пока не реализованы.

Этап 1: модульный FastAPI, PostgreSQL 17, SQLAlchemy 2, Pydantic 2, явный Alembic,
справочники departments/employees/locations, health probes, постоянные volumes.
Исходная миграция 0001_directories сохранена без изменений.

Этап 2:

- Argon2id, HttpOnly cookie-сессии; в БД только хеш bearer-токена, browser storage пуст.
- CSRF на входе и изменениях, точный Origin, атомарные лимиты входа в PostgreSQL.
- Четыре роли и серверные permissions; прямой admin API защищён независимо от меню.
- Пользователи: создание, роль, блокировка/разблокировка, временный пароль и обязательная смена.
- Отзыв сессий при смене/сбросе пароля, блокировке и изменении роли; защита последнего администратора.
- Bootstrap первого администратора через CLI со скрытым вводом; стандартного пароля нет.
- Отдельная runtime-роль БД без DDL, удаления пользователей и изменения аудита.
- React/TypeScript, Vite, Tailwind, shadcn/Radix, Router, TanStack Query, Lucide.
- Русский login, адаптивное меню, Dashboard, управление пользователями и профиль.
- Все восемь метрик недоступных модулей возвращают null; события берутся из настоящего аудита.
- Оригинальные логотипы сохранены; будущие разделы явно помечены «В разработке».

## Исправления после ревью

- Ожидающий административный запрос повторно проверяет исходную сессию после блокировки:
  отозванная сессия теперь получает 401 вместо выполнения изменения.
- Nginx заменяет XFF; закрытый от внешней сети backend получает фактический адрес клиента.
  Раньше IP-лимит был общим для всех пользователей proxy.
- URL/query не пишутся в access logs. PostgreSQL не выводит SQL, параметры и DETAIL строк.
- Зафиксирована полная цепочка Argon2-зависимостей в requirements.txt.
- Исправлены проверки и порядок действий deploy; подробности в плане выпуска.

## Перенос Windows → Ubuntu

Подготовлены RELEASE.md, DEPLOYMENT.md, отдельные staging/production конфигурации,
сборщик Linux images, manifest/контрольные суммы, install/update/backup и отдельный restore.
Проверки скриптов и реальная Docker-репетиция описаны в
`docs/superpowers/plans/2026-10-17-release.md`.
Репетиция выполнила install → HTTPS readiness → update с проверенным dump/files backup →
явный restore → сравнение синтетической записи и файла → HTTPS readiness.
Для неё использовались только отдельные e29-release-test контейнеры/volumes.

**Что остаётся проверить на предприятии:** первый запуск на настоящей Ubuntu 24.04,
root-права/владельцы каталогов, flock, systemd, SSH, внутренний DNS, сетевые ACL и
корпоративные сертификаты. Локальная репетиция использует Windows adapter и тестовый CA;
это не проверка инфраструктуры предприятия. ARM64-сборка не испытывалась.
Корпоративный сервер автоматически не развёртывался и не изменялся.

## Данные и границы

Все destructive tests выполнялись в отдельных disposable БД/volumes с вымышленными
данными. Пользовательский Compose-проект element29 не использовался для тестовых
созданий, блокировок, сбросов паролей или downgrade. `.env`, `.scratch`, тестовые пароли,
дампы и browser artifacts игнорируются Git. Исходники и данные во внешние облачные
сервисы не отправлялись. CartridgeDesk не изменялся, GLPI.xlsx не импортировался.

Локальный интерфейс: http://localhost:8080. Запуск, первоначальный администратор и
раздельный dev frontend/backend описаны в README.md. Результаты реального серверного
развёртывания следует добавить сюда после отдельной приёмки на предприятии.
