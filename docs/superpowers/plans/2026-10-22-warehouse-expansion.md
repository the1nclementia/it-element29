учётом физических экземпляров оборудования, едиными документами и фирменным UI.

количественные движения и перемещения экземпляров имеют разные инварианты.
**Стек:** Python 3.12+, SQLAlchemy 2, Pydantic 2, PostgreSQL, React/TypeScript,
TanStack Query, Radix, Tailwind, Docker Compose, Nginx.

## Правила исполнения

- Не переставлять шаги молча. Новые указания пользователя вносить в план с причиной.
- На один проход брать законченный проверяемый результат. Не оставлять заглушки
  под видом работающих функций и не объявлять будущие шаги готовыми.
- Перед поведением: тест → воспроизведённый отказ → минимальная реализация → проверки.
- После шага: отметить выполненные пункты, записать команды/результаты и следующую
  задачу в PROGRESS.md, проверить diff, создать локальный осмысленный commit.
- Основной стенд, `.env`, реальные данные и volumes не изменять. PostgreSQL-тесты —
  только новые изолированные БД и forward-миграции. Не выполнять DROP/TRUNCATE,
  downgrade, down -v, восстановление поверх данных, production deploy или git push.
- Авторизацию, cookie/CSRF, пароли и действующие роли сохранять. Новые операции
  защищать backend permissions; изменения матрицы прав сначала явно обосновывать.
- Не реализовывать списание, сложный ремонт/диагностику, CMDB, сетевое обнаружение,
  QR/штрихкоды, GLPI/Zabbix, жёсткий справочник адресов и обязательный табельный номер.
- Логотипы не перерисовывать; корпоративные данные не передавать облачным API.

## Архитектурные решения и границы

1. **Сохранить монолит и общие документы — рекомендуемый вариант.** Расходник
   учитывается количеством, оборудование — UUID экземпляров. Добавить
   `equipment` и неизменяемые `equipment_movements`, строки экземпляров связать с
   существующим документом. У оборудования current placement/version — источник
   текущего состояния; история хранит снимки до/после, автора и документ.
2. **Не объединять экземпляр с номенклатурой.** Явный режим учёта и вид товара
   задаются данными, не названием категории. Старые позиции остаются количественными;
   категории с похожими названиями автоматически не переклассифицировать. Изменение
   режима после операций запрещается без отдельного процесса переноса.
3. **Совместимость принтеров:** сохранить существующие ID printer_models и связи.
   Для принтерной номенклатуры добавить однозначную связь с PrinterModel; связанные
   названия/производитель изменяются одним сервисом, без независимых расходящихся копий.
4. **Номера — согласовано пользователем 22.10.** Inventory number уникален глобально,
   serial number — в пределах производителя. Пустые значения допустимы, UUID всегда
   обязателен. Хранить исходное значение и нормализованный ключ; уникальность
   непустых ключей обеспечивать PostgreSQL, включая архивные экземпляры. Пробелы
   по краям удалять, регистр ключа нормализовать; внутренние символы не выкидывать.
   Для двух пустых номеров показывать UUID и предупреждать о невозможности проверить
   физический дубль: гарантировать отсутствие такого дубля без идентификаторов нельзя.
5. **Один commit на операцию.** Общий application service блокирует все затронутые
   позиции/экземпляры в устойчивом порядке, проверяет версии, права и доступность,
   записывает документ/строки/оба вида движений/current state/аудит атомарно.
   Нижние сервисы не делают самостоятельный commit внутри смешанного документа.
6. **Ремонт:** отдельная отметка, а не статусы «Диагностика»/«Ремонт» вместо положения.
   Выдать можно только экземпляр на складе без отметки. Изменение отметки — отдельное
   контролируемое действие с причиной и аудитом. Возврат и отмена — разные операции.
7. **Миграционная развилка до шагов 3–4.** `ck_inventory_documents_valid_type`
   допускает только receipt/issue/reversal; у черновиков также ограничены типы.
   Новые return/replacement/transfer потребуют заменить CHECK в новой forward-миграции.
   Это не удаляет строки, но требует DROP CONSTRAINT, запрещённого буквальным правилом
   AGENTS.md. До такой миграции представить точный DDL и получить узкое разрешение
   на замену конкретных CHECK; общий запрет удаления данных не ослаблять. Альтернатива —
   новые таблицы документов и объединённая история, но она существенно усложняет
   смешанные документы/ledger и не выбирается молча. Старые миграции не редактировать.
8. Переписывание приложения или отдельный сервис оборудования не нужны: они
   усложнили бы общую транзакцию и сопровождение без пользы для этого ТЗ.
